# 概要とスコープ

## 1. 概要

ローカル PC 上で動く、開発者向けの API クライアント＋通信観測デスクトップアプリ。「通信を実行する → テストする → 観測する → 原因を分析する」という開発ワークフローを 1 つのアプリで支える。まず API クライアントとして完成させ、その後に通信観測機能を足していく。

### コンセプト

- ユーザーが URL・HTTP メソッド・ヘッダ・本文を自分で設定して API に直接リクエストを送り、レスポンスを確認・保存・テストできる。
- 将来は、明示的にプロキシを設定したブラウザから、自分のアプリ（localhost と本番環境）への HTTP/HTTPS 通信を観測・分析できる。観測は「見るだけ」で、通信の書き換え・中継・遮断はしない。
- 「別アプリの通信を自動で盗み見る」ものではなく、「自分でリクエストを発行し、自分の管理下の通信を観測する」ツール。

### 解決したい課題

- 動作確認のたびに同じリクエストを手作業で作り直す手間。
- 開発・テストなど環境ごとの URL・認証情報の切り替えの面倒さ。
- ステータスコード・ヘッダ・本文・通信時間をまとめて確認しにくい。
- API の期待動作をテストとして記録し、変更後に再確認したい。
- 実際のアプリで起きた通信の内容や失敗原因を調べ、再現可能なリクエストやテストに変換したい。

### 想定ユーザー

- Web アプリや REST API を開発するエンジニア。
- API を実装・検証する開発者。
- 開発・テスト環境で複数の API エンドポイントを扱う開発者。

### 技術スタック

| 担当 | 技術 | 選定理由 |
| --- | --- | --- |
| デスクトップアプリ | Tauri | 画面は慣れた Web 技術で作り、Rust の学習を送信・プロキシ・保存の中心部分に集中できる。 |
| フロント | TypeScript（Vite + React） | API 処理に慣れている TypeScript を採用。Tauri の中では Next.js のサーバー機能を使えないため、軽い Vite + React にした。 |
| バック | Rust | API の観測のため低レイヤー処理を扱える Rust を採用。送信は reqwest、プロキシは hudsucker、保存は SQLite（rusqlite）、非同期処理は tokio。 |

---

## 2. スコープ

最初からプロキシを作らず、**API クライアントを基本機能として完成させてから**、自動テスト・通信観測・両者の統合へと段階的に広げる。これにより、各段階で動くものが手に入り、挫折しにくく、設計も積み上げやすい。

### 最初にやること（基本機能）

ユーザーが自分でリクエストを組み立てて API に直接送り、レスポンスを確認・保存・テストする。これは「別アプリの通信を捕捉する」機能ではなく「自分でリクエストを発行する」機能。

### 後から足すこと（将来機能）

ローカルプロキシを使い、明示的にプロキシを設定したブラウザやテスト対象アプリの通信を観測する。さらに観測した通信を API リクエストやテストケースに変換し、クライアントと観測を統合する。

### やらないこと（意図的に外す）

- すべてのアプリの通信を自動検出すること。
- HTTP/2・HTTP/3・QUIC・WebSocket などあらゆる通信への対応。
- 証明書ピンニングを回避する機能。
- 複雑なスクリプト言語を備えたテストエンジン。
- チーム共有やクラウド同期。
- 独自のプロキシプロトコルや分散処理。
- 観測した通信の書き換え・中継・遮断（観測は見るだけ）。
- 外部サービスへの通信の観測（対象は自分のアプリの localhost と本番環境）。

> **注意**: HTTPS の中身を観測するにはプロキシ設定や CA 証明書の信頼設定が必要で、ピンニング等の制約で解析できないアプリもある。対象は**自分が管理するアプリや許可されたテスト環境に限定**する。
