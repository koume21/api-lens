# 開発フローと各フェーズ

## 5. 開発フロー（全体像）

API クライアントを先に完成させ、そこへ保存・環境・テスト・観測を積み上げる。前のフェーズの「完了の目安」を満たしてから次へ進むと、常に動くものが手元に残り、設計も積み上がる。P5（通信観測）が最難関。

```txt
P0 準備・土台
 └▶ P1 API クライアント MVP
     └▶ P2 保存と実用性
         └▶ P3 環境変数・認証・秘密情報
             └▶ P4 API テスト・シナリオ実行
                 └┄▶ P5 通信観測（実験・最難関）
                       └▶ P6 統合・品質向上・公開
```

| フェーズ | 目的 | 完了の目安 |
| --- | --- | --- |
| [P0 準備・土台](#p0-準備土台) | 開発を始められる状態を作り、「1 リクエスト送って表示」を一本だけ通す。 | ビルドが通り、ボタンを押すと固定 API のレスポンスが画面に出る。 |

## 6. 各フェーズの詳細

各フェーズは「目的・作る機能・自分で調べて決める問い・完了の目安・つまずきやすい点」で示す。**実装の答えは書かない**ので、どう作るかは自分で設計・調査する。

### P0 準備・土台

- **目的**: 開発を始められる状態を作り、「1 リクエスト送って表示」を一本だけ通す。
- **作る**: プロジェクトの初期構成、UI とロジックを分ける最小の骨組み、固定 URL に 1 回リクエストして結果を画面に出す。
- **自分で決める問い**:
  - 言語／フレームワーク → 決定済み：Tauri + Vite + React（TypeScript）と Rust（[設計](05-design.md#技術選定) の技術選定を参照）。
  - UI と通信処理の境界をどこに引くか。
  - ディレクトリ構成をどうするか。
- **完了の目安**: ビルドが通り、ボタンを押すと固定 API のレスポンスが画面に出る。
- **つまずきやすい点**: 最初の環境構築。深入りせず「動く最小」を優先する。

### P1 API クライアント MVP

- **目的**: 自分でリクエストを組み立てて送れる、アプリの核を作る。
- **作る**: メソッド選択、URL・ヘッダ・本文の編集、送信とキャンセル、タイムアウト、レスポンスのステータス／ヘッダ／本文表示、JSON 整形、エラー処理。
- **自分で決める問い**:
  - リクエストの送信場所 → 決定済み：ネイティブ側（Rust の reqwest）で送る。なぜブラウザの fetch ではなくこちらの方が CORS・Cookie・ヘッダの自由度で有利なのかは、自分で説明できるようにしておく。
  - 通信時間と受信サイズをどこで計測するか。
  - キャンセルをどう実現するか。
- **完了の目安**: 自作 API に対し GET・POST・認証付きリクエストを送れ、正常系・エラー系・タイムアウトを確認できる。
- **つまずきやすい点**: キャンセルの扱い、巨大／ストリーミングレスポンス、エラーの種類分け。

### P2 保存と実用性

- **目的**: 作ったリクエストを残して再利用できるようにする。
- **作る**: リクエストの保存・再実行、実行履歴、ローカル DB 導入、再起動後の保持。保存したリクエストの編集・複製（将来）、コレクション分類（将来）。
- **自分で決める問い**:
  - 「リクエストの定義」と「実行時点の結果」をどう分けて持つか。
  - DB のスキーマをどう設計するか。
  - 何を DB に、何をファイル（大きな本文など）に置くか。
- **完了の目安**: 再起動しても設定・履歴が残り、保存済みリクエストを再実行できる。
- **つまずきやすい点**: 定義と結果の混在、スキーマの後からの変更（マイグレーション）。

### P3 環境変数・認証・秘密情報

- **目的**: 環境を切り替えて同じリクエストを使い回し、秘密情報を安全に扱う。
- **作る**: 変数定義と環境切替（将来）、URL・ヘッダ・本文での変数参照（将来）、Bearer／Basic（今回はヘッダー手入力で対応。専用の入力欄は将来）、Cookie 管理（将来）、ログインで得たトークンの後続利用（将来）、トークン・API キーの安全な保管（将来）。
- **自分で決める問い**:
  - 変数の解決順序をどうするか。
  - 秘密情報をどこに置くか（OS の資格情報ストアか、暗号化か）。
  - ログ・履歴・エクスポートに秘密が漏れないよう、どこで止めるか。
- **完了の目安**: 環境を切り替えて同じリクエストを実行でき、トークンが平文で散らばっていない。
- **つまずきやすい点**: 秘密情報の分離、マスキングの入れ忘れ。

### P4 API テスト・シナリオ実行

- **目的**: 期待動作をテストとして記録し、変更後に再確認できるようにする。
- **作る**: ステータス・本文・時間のアサーション（将来）、複数リクエストの順次実行（将来）、前のレスポンスから値を取り出して次へ渡す（将来）、結果と失敗理由の一覧（将来）。
- **自分で決める問い**:
  - アサーションをどんなデータ構造で表すか。
  - リクエスト間の値の受け渡しをどう設計するか。
  - 失敗箇所と理由をどう表現するか。
- **完了の目安**: ログイン → データ取得のシナリオを実行し、どの段で何が失敗したか特定できる。
- **つまずきやすい点**: 値の受け渡しの設計、シナリオ途中で失敗したときの扱い。

### P5 通信観測（実験・最難関）

- **目的**: 自分の管理下の通信をプロキシ経由で観測する。
- **作る**: ローカルプロキシの起動・停止、プロキシ設定したブラウザから自分のアプリ（localhost と本番環境）への通信観測、一覧・詳細・フィルタ、保存、再送。観測は見るだけで、書き換え・遮断はしない。
- **自分で決める問い**:
  - HTTPS の中身を見るには何が必要か（ローカル CA、リーフ証明書、信頼設定の流れ）。方針は決定済み：hudsucker で自分専用の CA を作り、Mac への信頼登録は手作業で行い、鍵は PC の外に出さない。仕組みは自分で説明できるようにする。
  - 最初に対象を HTTP/1.1 に絞る範囲と限界はどこか。
  - 観測した 1 件をどんなデータ構造で持つか。
- **完了の目安**: 自分が管理するテスト用 Web アプリの通信を、プロキシ経由で観測できる。
- **つまずきやすい点**: ここが最難関。CA の信頼設定、TLS の終端、そして証明書ピンニングするアプリは観測できないという制約。いきなり HTTPS に挑まず、まず HTTP の素通し観測から段階を踏むとよい。

### P6 統合・品質向上・公開

- **目的**: 全体を仕上げ、他人が触れる状態にする。
- **作る**: 観測した通信を API リクエスト／テストケースへ変換、過去結果との比較、UI・通信・保存の統合テスト、Windows／macOS の動作確認、README・アーキテクチャ図・設計判断・デモの整備。
- **自分で決める問い**:
  - 観測フローと保存リクエスト／テストを、どう共通のデータモデルに写すか。
  - 何をもって「完成」とするか。
- **完了の目安**: 初見の開発者が README を見て起動し主要機能を試せ、制約・設計判断・セキュリティ上の注意を自分の言葉で説明できる。
- **つまずきやすい点**: データモデルの不一致、OS 差の動作確認。
