# 開発プロセスと工程ごとの中身

## 7. 開発プロセス（要件定義〜設計〜実装〜テスト）

P0〜P6 が「何を作るか」の順序なら、この章は「どう作るか」の工程。各フェーズの中で、要件定義 → 設計 → 実装 → テスト の 4 工程を小さく回す。最初から完璧に設計しようとせず、1 フェーズ分の小さなサイクルを繰り返すのがコツ。

```txt
要件定義 ─▶ 設計 ─▶ 実装 ─▶ テスト
              ▲        │        │
              └────────┴────────┘
          （気づいたことを設計へ戻す）
```

きれいに一方向で進むのではなく、テストや実装で気づいたことを設計へ戻す反復が前提。各フェーズでこのサイクルを一周させる。

## 8. 工程ごとの中身

各フェーズ（P0〜P6）の中で、この 4 工程を回す。ここでも実装の答えは示さず、各工程で「作る成果物」と「決めること」を挙げる。

### 要件定義

- **目的**: そのフェーズで「何ができれば完了か」を言葉にする。
- **作る成果物**: ユーザーがやりたいこと（ユースケース）、満たすべき条件（受け入れ条件＝完了の目安）、やらないことの線引き。
- **決めること（問い）**: このフェーズの最小の価値は何か。何を今はやらないか。
- **完了の目安**: 「このフェーズのゴール」を 1〜数行で書き出せている。

### 設計（具体的に）

このアプリで設計すべき成果物は、おおむね次の 6 つ。各成果物について「決める問い」を自分で埋めていく（答えはここには書かない）。

1. **データモデル（最重要）**: 主要エンティティと関係を決める。
   - 問い — Environment / Collection / RequestDefinition / ExecutionResult / TestCase / Flow / SecretRef をどんな属性で持ち、どう関連づけるか。「リクエストの定義」と「実行時点の結果」をどのテーブルで分けるか。大きな本文はどこに置くか。
   - 成果物 — ER 図（または簡単なスキーマ表）。
2. **モジュール構成と責務**: UI・HTTP 通信・永続化・テスト実行・（将来）プロキシ・秘密情報 をどう分けるか。
   - 問い — どのモジュールが何を知ってよく、何を知ってはいけないか。モジュール間のインターフェース（内部 API）はどんな形か。
   - 成果物 — モジュール図と責務一覧。
3. **UI・画面設計**: どんな画面があり、どう行き来するか。
   - 問い — リクエスト編集・レスポンス表示・履歴／一覧をどう配置すれば行き来しやすいか。
   - 成果物 — 画面構成と遷移のラフ。
4. **通信・エラー設計**:
   - 問い — 送信・キャンセル・タイムアウトをどう表現するか。エラー（接続失敗・タイムアウト・不正 JSON・HTTP エラー）をどう型／状態で区別し、UI にどう出すか。
   - 成果物 — 状態遷移やエラー分類の整理。
5. **変数・認証の設計**:
   - 問い — 変数の定義と解決順序、環境切替、そしてログインで得たトークンを後続へ渡す仕組みをどう設計するか。ここが確認事項 Q2 の核心で、「ログイン済みか」ではなく「各リクエストに認証情報（Bearer トークン／Cookie／Basic）をどう載せ、ログインのレスポンスからどう取り出して次へ渡すか」を決める。
   - 成果物 — 変数解決とトークン受け渡しの流れ図。
6. **セキュリティ設計**:
   - 問い — 秘密情報をどこに置くか、ログ・履歴・エクスポートのどこでマスキングするか、HTTPS 観測を有効化・停止する境界をどこに引くか。
   - 成果物 — 秘密情報の保管場所とマスキング境界の一覧。

> **設計の完了の目安**: 上の 6 つについて「実装前に、他人へ 5 分で説明できる」状態。図とスキーマが揃い、迷いどころに自分なりの答えが出ている。

### 実装

- **目的**: 設計を動くコードにする。
- **進め方**: 「一番薄く縦に貫く 1 機能」から着手し、小さく動かして広げる。設計どおりにいかなければ設計へ戻す（反復）。
- **作る成果物**: 動くコードと、こまめなコミット。
- **完了の目安**: そのフェーズの受け入れ条件（要件定義で決めたもの）を満たす。

### テスト

- **目的**: 作ったものが期待どおり動き、後で壊れていないかを確かめられるようにする。
- **レベル**: ユニット（変数解決・アサーションなどロジック）／統合（HTTP 通信をモックサーバ相手に）／手動または E2E（主要シナリオ）。
- **決めること（問い）**: このフェーズで「壊れたら困る」のはどこか。そこをどのレベルでテストするか。
- **完了の目安**: 受け入れ条件がテストで（または手順で）確認でき、次フェーズに進んでも後戻りしない。
