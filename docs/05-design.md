# 設計

2026-10-24 に決めた設計（フォルダ構成は 2026-10-29 決定）。要件は [04-requirements.md](04-requirements.md)。

## 技術選定

| 部品 | 役目 | 使うもの |
| --- | --- | --- |
| 画面（UI） | 一覧・詳細・送信画面を表示する | Tauri + Vite + React |
| 送信役 | ①で入力したリクエストを送る | reqwest |
| 関所（プロキシ） | ブラウザの通信を受け取って記録し、本来の相手に渡す。HTTPS の中身も見る | hudsucker |
| 保存係 | 保存したリクエストと履歴を PC に残す | SQLite（rusqlite） |
| 裏方 | 通信を待ちながら画面にも反応する（非同期処理） | tokio |

## 全体の構成

ブラウザ → 関所 → API サーバー の途中で通信が記録される。自分で送るときは 画面 → 送信役 → API サーバー。関所と送信役の結果は保存係に残る。画面と Rust 側は、Tauri の「コマンド」（画面から頼む）と「イベント」（Rust から知らせる）でやり取りする。

```txt
                 ┌──────────── デスクトップアプリ ────────────┐
                 │                                            │
                 │  画面（React）                             │
                 │    │  ▲                                    │
                 │ コマンド イベント                           │
                 │    ▼  │                                    │
ブラウザ ──────▶ │  関所（hudsucker）──▶ 保存係（SQLite）◀── 送信役（reqwest）
                 │    │                                    │  │
                 └────┼────────────────────────────────────┼──┘
                      ▼                                    ▼
                                 API サーバー
```

## 処理の流れ

### A. 観測モード（④〜⑧）：API を叩くのはブラウザの自分のアプリ

1. 画面で「観測開始」を押すと、関所が待ち受けを始める
2. ブラウザで自分のアプリを操作し、API への通信が発生する
3. ブラウザはプロキシ設定に従い、その通信を関所に渡す
4. 宛先が登録した対象ホストなら、関所が中身を記録して本来の API サーバーへ渡す。対象外なら中身を開かずにそのまま通す（F21）
5. API サーバーの返事も関所を通り、記録されてからブラウザへ戻る
6. 関所が画面に「新しい通信」を知らせ（イベント）、一覧に 1 行増える

### B. 送信モード（①〜③）：API を叩くのはデスクトップアプリ

1. 画面で URL・メソッド・本文を入力して「送信」を押す
2. 画面が Rust 側の送信役に頼む（コマンド）
3. 送信役が API サーバーへ送り、返事を受け取る
4. 結果を保存係に残し、画面に表示する

## DB 設計（論理）

SQLite に表を 3 つ作る。ヘッダーは名前と値のペアを JSON 文字列にして 1 列に入れる。型やインデックスなどの物理設計は実装時に決める。

### 表1：通信の記録（観測と送信の両方。最新 1,000 件まで）

- 番号、日時、種類（観測 / 送信）
- メソッド、URL、リクエストヘッダー、リクエスト本文
- ステータスコード、レスポンスヘッダー、レスポンス本文
- かかった時間（ms）、サイズ
- 本文省略フラグ（N3）、エラー内容

### 表2：保存したリクエスト（F9、F10）

- 番号、名前、メソッド、URL、ヘッダー、本文、作った日時

### 表3：観測対象ホスト（F21、F22）

- 番号、表示名（例：ローカル、本番）、ホスト（例：`localhost:3000`、`api.example.com`）、作った日時

## 画面の構成

画面は 2 つで、上のタブで切り替える。観測対象ホストの登録は、観測画面の「対象ホスト」ボタンから開く小さな設定画面（ダイアログ）で行う。

### 画面1：観測（DevTools の Network タブに近い形）

- 上：表示する対象の切り替え（すべて / 登録したホスト）と「対象ホスト」設定ボタン（F21、F22）
- 上：「観測開始 / 停止」ボタン、URL 検索欄、成功 / 失敗の切り替え、履歴削除ボタン（F11、F14、F15、F20）
- 左：通信の一覧。時刻・メソッド・URL・ステータス・時間（F12、F18）
- 右：選んだ 1 件の詳細。「送った内容」と「返ってきた内容」をタブで切り替え（F16）
- 詳細に「送信画面にコピー」ボタン（F17）

### 画面2：送信（API クライアントに近い形）

- 左：保存したリクエストの一覧。クリックで読み込む（F10）
- 右上：メソッド選択、URL 入力、「送信」「保存」ボタン。その下にヘッダー / 本文の入力タブ（F1〜F4、F9）
- 右下：結果。ステータス（成功は緑・失敗は赤）、時間、サイズ、ヘッダー / 本文のタブ（F5〜F8）

## フォルダ構成

2026-10-29 決定。`src` が画面、`src-tauri` が Rust 側で、構成図の境目がそのままフォルダの境目になる。

```txt
<アプリ名>/
├─ src/                 ← 画面（React / TypeScript）
│  ├─ pages/            観測画面・送信画面
│  ├─ components/       一覧、詳細、リクエスト入力、結果表示、ホスト設定など
│  ├─ api/              Rust を呼ぶ窓口（コマンド呼び出し・イベント受信）
│  └─ types/            データの形（TypeScript 版）
├─ src-tauri/           ← Rust 側
│  ├─ src/
│  │  ├─ main.rs        起動するだけ
│  │  ├─ lib.rs         Tauri の準備とコマンドの登録
│  │  ├─ commands/      画面からの依頼を受ける受付
│  │  ├─ client/        送信役（reqwest）
│  │  ├─ proxy/         関所（hudsucker・証明書）
│  │  ├─ store/         保存係（SQLite：表1〜3）
│  │  └─ models/        データの形（通信1件、保存リクエスト、観測対象ホスト）
│  ├─ Cargo.toml        Rust の道具の一覧（npm の package.json に当たる）
│  └─ tauri.conf.json   アプリ名や窓の設定
└─ package.json / vite.config.ts など
```

- Rust 側は部品ごとに 1 フォルダ。画面とやり取りするのは `commands` だけで、送信役・関所・保存係は画面のことを知らなくてよい
- 観測対象ホスト（F21・F22）は `store`（表3）、`commands`（登録・削除）、画面の `components`（ホスト設定）に入る
- 最初から全部は作らない。P0 では `commands` と `client` だけ作り、必要になったら増やす

## 認証と証明書

- **認証**：専用の入力欄は作らず、ヘッダーに手で入力する（例：`Authorization: Bearer xxxxx`）。必要になったら後で足す
- **証明書（F13）**：初回起動時に、アプリが自分専用の認証局証明書を作る（hudsucker の機能）
- **証明書の登録**：Mac への登録は、アプリが手順を表示して自分で手作業で行う。アプリは勝手に登録しない
- **証明書の鍵**：自分の PC の中だけに置き、他人に渡さない。漏れると「偽のサイト」を本物に見せかけられてしまうため
